\begin{abstract}
A fundamental hurdle in trading is the balance between market impact and
alpha decay. Submitting a large order leads to significant price impact
as it takes the liquidity from the Limit Order Book (LOB). On the other
hand, splitting a large order into smaller chunks over seconds or
minutes exposes unexecuted orders to alpha decay and price drifts. This
hurdle is especially prevalent in crowded markets where thousands of
algorithms are trading on similar signals.

Our goal is to measure the average alpha lost when forced to split
orders by comparing different execution strategies. This milestone
report quanitifies our progress toward this goal. We use markout plots
to analyze order book imbalance (OBI) as a predictor to help minimize
the cost of chunking orders through price drifts and impact. We then
build and validate an order execution simulator, and compare three
execution strategies for a large-cap-small-tick equity.
\end{abstract}


\section{Goals for the Milestone}\label{goals-for-the-milestone}

The goals we have set for this milestone report are as follows.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Build a data ingestion pipeline, which can parse L2 order book data
  from Databento for use in our \texttt{ExecutionSimulator}. It should
  use caching for speed improvements and API savings.
\item
  Explore the effectiveness of order book imbalance (OBI) as a predictor
  of short term price movements via markout plots. We should use these
  plots to inform an execution strategy using OBI.
\item
  Write an \texttt{ExecutionSimulator} which can simulate the effects
  and performance of multiple execution strategies. It should be able to
  simulate multiple execution strategies, and the effects latency and
  limit order replenishment on the book.
\end{enumerate}

\section{Sourcing Data}\label{sourcing-data}

We are using the \texttt{MBP-10} schema from Databento, which provides
the top 10 levels of the Limit Order Book (LOB) for a selection of
stocks and date range. The dataset includes all order book updates
(trades, adds, cancels, etc.) which allows us to reconstruct the market
dynamics at a granular level. The data is sourced from
\href{https://databento.com/docs/schemas-and-data-formats/mbp-10?historical=python&live=python&reference=python}{Databento}.
We fetch data through a simple \texttt{MBP10DataAdapter} class that uses
a hierarchical caching structure. This allows us to call the Databento
API only when necessary, which is necessary for L2 book data. The
adapter caches on
\texttt{{[}tickers,\ start,\ end,\ dataset,\ schema{]}}. Here, our
schema is always \texttt{MBP-10} and we use the \texttt{XNAS.ITCH}
Dataset which gives us full access to the Nasdaq exchange.

We use L2 data for \texttt{AMZN} from
\texttt{"2026-03-25":"2026-03-27"}. We are intentionally using a small
time range and a single large-cap-small-tick stock in order to minimize
runtime and memory requirements and maximize order book liquidity while
we develop the simulator and strategies. Through the end of the project,
we will add multiple assets spanning the large/small market cap and
tick-size range to explore how different assets require different
execution strategies.

\section{Markout Plots}\label{markout-plots}

The execution strategy we are building toward uses OBI to determine
``good'' or ``bad'' times to fill, and only fills at ``good'' times.
However, first we need to explore how well OBI can separate the ``good''
and ``bad'' times to fill. We define order book imbalance (OBI) as: \[
\begin{split}
OBI = \frac{Q_{bid} - Q_{ask}}{Q_{bid} + Q_{ask}}\in [-1, 1]
\end{split}
\]

OBI ranges from \([-1,1]\) and is known to be a good structural
predictor of subsequent short-horizon returns. By capturing the relative
quantity at the best bid and ask, OBI indicates which level will likely
deplete fastest as aggressive orders arrive. To explore OBI's predictive
power, we use markout plots. For each of five ranges of OBI values, we
sample 100,000 start times and calculate the difference between the
initial mid-price and the mid-price at 10,000 subsequent times, then
average over each of the 100,000 paths. We use a time horizon of
\([0,10]\) seconds, in milliseconds.

\caption{10s Markout Plot}

\end{figure}%

We can clearly see that OBI is a good predictor of price direction
within a few milliseconds and that this price motion is structural,
indicated by the length of time that the prices take to revert. In fact,
for \(|OBI| \in [0.5, 1]\) the price does not on average revert. This
gives good grounding for OBI's use in our execution strategy.

\section{Execution Simulator}\label{execution-simulator}

Our final goal for the milestone is to have built an
\texttt{ExecutionSimulator} class which can:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Simulate the execution of market orders and immediate-or-cancel (IOC)
  limit orders at a given nanosecond timestamp and latency.
\item
  Maintain an orderbook state over time, using L2 data from the
  \texttt{MBP10DataAdapter}, consistent with mutations of the book
  caused by simulated fills and the replenishment of the book via a
  Poisson process.
\item
  Simulate three filling strategies of a large parent
  order(Q\textgreater10,000):

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Immediate/Naive: Attempt to fill the entire large order at once,
    sweeping all 10 levels.
  \item
    Constant Rate Naive: Split the parent into \(n\) chunks of size
    \(q/n\) and execute them \(\delta t\) seconds apart, at a constant
    rate.
  \item
    OBI-Aware: Fill child orders of quantity \texttt{max\_size} only
    when \(|OBI| > threshold\) (positive for buys, negative for sells).
    This ensures the child orders fill only when the price is at a local
    minimum (buys) or maxiumum (sells).
  \end{enumerate}
\end{enumerate}

To achieve these goals we wrote the \texttt{ExecutionSimulator} class
which initiates the L2 book with a \texttt{polars} dataframe in
Databento's \texttt{MBP-10} schema. The simulator maintains the book
using internally consistent \texttt{numpy} arrays, which it updates as
the book changes with after simulated fills. At the end of a simulation
it returns a new \texttt{polars} dataframe representing the mutated book
over time, as well as a dictionary of the form below. Note that
\texttt{arrival\_cost} is calculated as the \texttt{vwap} minus the mid
price at execution.

\subsection{Initial Execution
Comparison}\label{initial-execution-comparison}

After verifying the correctness of the \texttt{ExecutionSimulator}, we
can briefly compare strategies. Plots of these execution results can be
found at Figure~\ref{fig-execution} in Section~\ref{sec-appendix}. All
three strategies ran with 5ms latency, replenishment rate of
\(\lambda = 10\), and a parent buy order for 10,000 shares. The naive
execution could only fill 2,432/10,000 shares, and the repeated naive
execution filled all 10,000 with a total cost of of \$2.5, calculated as
the sum of the difference between each fill's VWAP and the mid-price at
the time of execution, and a summed arrival cost of \$1.5. The OBI-aware
strategy improved on this with a total cost of \$2.1 and a summed
arrival cost of \$0.53.

Beyond the milestone, our main goals are to:

\end{enumerate}
